# crazyAgent development contract

## Change one observable milestone at a time

Define the smallest user-visible behavior that can be checked independently, take a real-run baseline, change one main thing, then rerun the same scenario from the same initial state. Compare success, partial completion, and collateral edits; wall time, model steps, and tool calls; failed calls, retries, and wrong-target actions (even if repaired); and tokens when relevant.

Keep the model and reasoning effort fixed for comparisons. Acceptance uses **medium effort**; do not compare with older off/low runs. New configurations default to **Auto**: low for `act`/`navigate`/`rapid`, medium for `inspect`/`synthesize`, using the raw user prompt supplied through `turn.context`; saved choices apply unless an explicit process CLI/env effort override is supplied. A recovered mistake is still reliability evidence.

## Independent checks decide

Logs, screenshots, model reasoning, `turn.ok:true`, `changed:true`, DOM mutations, trusted input, pixel differences, and the agent saying "done" are diagnostics, not proof. Inspect the resulting browser or document state independently of the tool result and final answer. With no checker, ask the user for a verdict: correct, partial, wrong, or blocked. Use console probes only for a specific diagnostic or ground-truth question.

## Regression gates

Use the cheapest gate that can detect the change, then the next:

1. `npm test` for contracts, validation, serialization, and state handling.
2. Real-extension fixture suites for executor changes (`scripts/edge-*-e2e.mjs`). They inspect page state directly but do not evaluate model decisions.
3. A complete real-sidebar scenario for behavior changes, from a known initial state with independent final-state inspection. `scripts/model-eval.mjs` runs scripted real-model scenarios on an isolated profile with independent checkers.

Panel UI changes also run `scripts/ui-preview.mjs --scenario <name>` (mock bridge). Never present unit tests, mock-bridge previews, or direct-executor suites as real-model acceptance. Repeat important model-driven scenarios enough to tell a lucky run from reliability.

## Current focus: Google Docs and semantic editing

Use Docs as a stress test for transferable primitives: exact text targeting, selection, canvas input, layout, menus, and verification. Prefer stable semantic operations for repeated dependent workflows without weakening the general browser tools. Keep stale-view, ambiguity, wrong-target, scoped-recovery, native-dialog, and verification safeguards; if a UI transition invalidates coordinates, avoid coordinates or keep explicit operation state rather than relaxing guards.

Priorities: (1) exact deletion/replacement preserving formatting and neighbors; (2) formatting an exact unique or explicitly ordinal range; (3) compound document creation and formatting in a fresh disposable document; (4) authenticated semantic-table acceptance with collateral-cell and persistence checks. Duplicate text needs an explicit ordinal; never alter an arbitrary occurrence.

## Invariants to keep

- **Tools:** 34 standing model-facing tools (25 general, 8 guarded Docs, `agent_request_help`); `/marathon` (unlisted legacy alias `/plan`) adds `browser_plan` for every turn that starts while the companion-owned marathon switch is on, and the companion's opt-in `confirmIrreversible` setting adds `agent_request_confirmation` for its turns only (both conditionals can coexist). A legacy one-shot `planMode:true` message still works: it turns the shared switch on with the sender's origin, then arms the turn. Marathon M1–M5 are landed (rename + shared switch; plan carry-over + refill limits; deterministic watch ledger + alerts; the model judge; phone chip/watch card/checklist/WATCH push); the M6 release docs ship with v2.4.0 per `MARATHON-PLAN.md`. In M2 a turn that ends with open plan items carries the list into the next turn (`seedPlanState`, fail-closed `plan.seed.rejected` fallback); completion nudges and stale reminders refill per accepted revision (2 per stretch) under a 12-per-turn lifetime cap; a seeded-but-untouched turn (no `browser_plan` call, zero tool results) answers `not-assessed` without nudges (verified by the M2 unrelated-question real-model suite, 5/5; the v2 V4 live ×5 put model seeded-untouched reliability at ~60% — the rule and detection hold, the model sometimes resumes the carried plan, a model-variance finding not a regression). **V8 plan friction (§3.9):** `browser_plan` items gain an optional single-line `reason` (≤240 chars) allowed **only on `blocked` items** (any other status → `PLAN_REASON_STATUS`); an open item moving to `blocked` may change its content **without** `acknowledge_open_removal` when the new content **starts with** the old (the " — blocked: …" suffix), anything else still a rewrite needing ack; `PLAN_IN_PROGRESS_REQUIRED` stays and its message adds "mark them blocked too, or ask the user with `user_input_needed: true`". Every carry-chain validator (`plan.js` `normalizeItems`/`seedPlanState`, `prompt.mjs` `normalizePlanSeed`, `marathon.mjs` `normalizeMarathonPlan`, the hub, `plan-panel.js`, the Android reducer) accepts and keeps `reason` so a carried seed with a reason is not silently rejected; the panel and phone show the reason under a blocked item. Marathon v2 (V1–V8) ships with v2.5.0 per `MARATHON-V2-PLAN.md`. Mutations run exclusively in model order; only `browser_tabs`, `browser_places`, `browser_read_text`, `browser_docs_read`, and `browser_downloads` are parallel-safe.
- **Fail closed:** ambiguity, stale or drifted views, unsupported frames, paths outside Downloads, and unavailable colors fail with a code instead of guessing or substituting. ctrl/cmd+W is rejected in code.
- **Editable/chat targeting:** visible editable roots (`contenteditable`, ARIA textbox/searchbox) receive bounded labels; nested editable descendants and page-dominating editable surfaces stay excluded. Coordinate clicks report bounded pre-input hit identity and post-click focus as diagnostics only, never verification or a retry/re-aim trigger. Synthetic image paste suppresses the drop fallback only when scoped image insertion is observed, and reports target/placement uncertainty rather than claiming success.
- **Refusals stay refusals:** a pre-input `STALE_VIEW`/`AMBIGUOUS_VIEW`/`NO_VIEW` refusal of `click_at`/`select`/`drag` returns `attempted:false` with a fresh full view (text starts `refused <CODE>:`, counted as a failed call), and the same coordinates stay refused until re-measured on a newer view. A drag or selection on an iframe/canvas/video surface reports `unknown`, never a measured no-op. After two consecutive `SIDE_PANEL_CLOSED` results, browser calls fail at once until one succeeds or a new turn starts.
- **Dead model steps are retried in the same turn, never in a new one:** a step whose tool call arrived as DSML text (or, before any tool call, an empty step) gets at most two `agent.steer` notices in a row; a `followup` would start a new turn without the turn's conditional tools. An output-token (max-tokens) cutoff is continued the same way — one `agent.steer` per stopping event, keeping the turn's conditional tools armed. Internal notices use visible source kinds (`agent-notice`, `token-limit-continuation`), never `runtime-context` (the DSH loop replaces that kind with its context snapshot, so the text would never reach the model), and claiming one never resets the turn's repeat guard, executor circuit, no-progress count, or prompt tracking. A turn the runtime ends on `MALFORMED_RESPONSE`, `TRANSPORT` (after the provider's own retries), or `MODEL_SWITCH_COMPACTION_FAILED` before any action is rerun once by the companion with the turn's modes re-armed: a model-switch failure happens before the runtime commits the prompt, so the prompt itself is resent (unless a `user/message` was seen); otherwise a continue notice is sent. Request failures read "The model request failed (CODE)", not "the model's reply could not be used". A turn that still did nothing ends as an error or a `BLOCKED:` answer, never as a blank success or raw markup.
- **Evidence is separate from outcome:** results keep `observed`, `expectation`, `outcome`, and `mutationPossible` apart. A failed expectation never triggers re-aiming, retry, or re-mutation. DOM readback is not server persistence. Model-reported `DONE`/`PARTIAL`/`BLOCKED` labels, completed plan items, and `docsVerification` are not verification. URL-sensitive batch expectations (`export_contains`, `toolbar_style`) after a potentially document-changing step are rejected before side effects; page-scoped `text_landed` (a click) is allowed there and reports unknown on scope-mismatch — never a false verdict, no re-mutation. This relaxes evidence validity only; each step's stale-view/ambiguity/wrong-target mutation guards still apply.
- **Docs semantic fidelity:** HTML export parsing honors exact `text-decoration` declarations and ancestor underline/strike-through, not `text-decoration-skip-ink` or a child's `none`. Google may flatten checklists to bullets plus line-through: checklist writes require live checklist-control evidence at start and completion plus exported checked-state styling; never infer checklist identity from bullets alone. Font additions accept exact `Remove <font>` evidence when row checked state is unavailable, still require final toolbar verification, and close the modal on failure. Visible native table grids create and fill cells without the system clipboard (the status is columns × rows); larger grids retain clipboard-preserving paste. Responsive formatting uses baseline export only for uniform bold/italic/underline selections after an exact control-not-found, with final export verification; ambiguous states still fail closed. Below about 1300 CSS px (a docked side panel leaves ~1160) Docs moves the list buttons into an overflow that its More button opens; Docs marks that button `aria-disabled` although clicking it works, so the toolbar probe refuses only a natively disabled More, and every overflow reveal is followed by refocusing the document (the click otherwise sends later keystrokes to the toolbar). Write verification fills a span's missing font, size, or color from the export's element rules (`p{}`, `li{}`, `h1{}`–`h6{}`), never over an explicit value, and a failure names the first differing run and attribute.
- **Lifetime agent-token usage:** `companion/lifetime-usage.mjs` atomically persists aggregate finalized token-bearing turns (panel and remote; done, stopped, and error) to `.dsh-home/browser-agent/usage.json`, deduping recent turn IDs. `chat.hello.lifetimeUsage` restores the Settings meter and `usage.updated` refreshes it. Input/cache-read/cache-write/output are disjoint; reasoning is an output subset; watcher/judge tokens stay separate. Release updates preserve this file, while an explicit full clean deletes it. Tracking starts with the first turn recorded by this feature rather than reconstructing history from pruned logs.
- **DSH deep-freezes committed session events:** never annotate `turn/end`. Help, confirmation requests, plan outcomes, and Docs verification travel as bridge activities (`help-request`, `confirm-request`, `turn-outcome`) accepted only for the active turn and session.
- **Confirmation is opt-in and model-reported:** with `confirmIrreversible` off, behavior is exactly as before. With it on, the model is told to ask before irreversible actions and the chat waits for an Approve/Deny that the companion writes as the next turn's `<user_confirmation>` block; the model-reported tool is the primary mechanism, and an executor backstop covers a turn that skips it: in a turn with the setting on that did not start from the user's Approve, the companion stamps `click`/`click_role`/`batch`/`type` commands and the executor refuses, before input, a control whose name matches the reviewed list in `CONFIRM_GUARD_PATTERN` (or a native submit control of a POST form, or `submit:true`) with `CONFIRMATION_REQUIRED`. Enter-key submits and coordinate clicks are not covered. A confirmation wait is not verification that the action was safe.
- **One runner, one turn slot:** chat, new, stop, resume, steer, and snapshots go through `companion/session-controller.mjs`, shared by the panel and the remote API. The marathon switch is the same: one companion-owned state (`companion/marathon.mjs`), changed only through `SessionController.setMarathon`, published as `marathon.state`; clients render it and never assume or optimistically flip it. It resets to off on `/new`, a real chat switch, and companion restart (fail-safe).
- **The watcher only reports (M3 deterministic + M4 judge landed):** `companion/watch-ledger.mjs` (pure) records every turn — marathon or not — so a mid-turn toggle has history; `assess()` (pure) applies the §3.3.2 signal table plus the M4 `REVISIT_HINT` soft signal backed by bounded per-turn aggregates (whole-turn fingerprint and navigation-revisit counts, open-item trajectory). **V3 page identity (§3.4):** the `REVISIT_HINT` mutation-revisit branch is **page-scoped** — an effectful act repeated on the **same page** (best-effort page key from the most recent URL-naming result) against the **same control** (parsed `clicked label N: <role> "<name>"` / `typed into [N]`) with the **same outcome**, threshold 2; an unknown page key excludes the call (fails toward silence), so healthy multi-page work no longer conflate into false revisits. Navigation revisits stay digest-only; `REPEAT_LOOP` is unchanged. The judge digest carries V2-equivalent bare `mutationRevisits` (the pageKey/controlName annotation was removed — a measurement-justified deviation: it biased the judge toward reading cross-page navigation as exploration and reduced caught; pageKey/controlName remain in the ledger aggregates as a replay-only metric, page-unknown share ~4%). **V2 progress accounting (§3.3):** the ledger classifies tools as observe (the read-only list), control (`browser_plan`/`agent_request_help`/`agent_request_confirmation` — excluded from FAIL_STREAK/SAME_ERROR/REPEAT_LOOP/OBSERVE_ONLY, the mutation counters, and recovery; a `PLAN_*` error is plan friction, not a stuck browser; plan calls still feed the plan snapshot via activity), and act (page actions). An ok act result matching the provider's `NO VISIBLE CHANGE` marker is **no-effect** — the predicate `noProgressResultText` is exported from the provider (`lib/repeat-guards.js`, re-exported `lib/index.js`) and imported by the ledger so both sides agree by construction. The soft signal `NO_EFFECT` (≥4 of the last 8 act results no-effect) never alerts alone, brings the judge call forward, and corroborates a stuck verdict under two-strike. A plan update is not progress: only an effectful page action or a higher completed count clears an alert. `companion/watcher.mjs` ticks every 20 s on a marathon turn and alerts on hard signals (SILENT_STALL/TOOL_HANG/EXECUTOR_DOWN) without the model. The M4 judge (`companion/watch-judge.mjs`) is ONE stateless tool-less chat-completions call per check through injected getters over the companion's existing key/baseUrl/model — no bridge, no runner, no tools, so it cannot act; the key flows only into the Authorization header and is never logged. **V5 judge stability (kept change):** the request pins provider routing — `provider:{order:['morph'],allow_fallbacks:false,require_parameters:true}` — and a fixed `seed`, removing the temp-0 verdict instability caused by OpenRouter load-balancing each request across ~50 endpoints/quantizations; `require_parameters` guarantees the provider supports seed + reasoning (morph/fp8 does; PrimeIntellect lacks seed and is avoided). The pin and seed are sent only for the measured configuration, `deepseek/deepseek-v4.1-flash-1017` on `openrouter.ai` (`judgeRoutingPinned`); any other model or base URL sends the unpinned request, because Morph serves little of OpenRouter's catalog and a pinned call it cannot serve fails. Judge effort stays **low** and `max_tokens` **400** (V5 candidate 2's medium-requested/1200 raise was tested and NOT kept — its aggregate gain was contaminated-driven and the clean target regressed). **V4 continuation context (§3.5):** an accepted plan seed emits ONE `bridge.activity {kind:'plan', revision, items, awaitingUser:false, seeded:true}` at turn start so the ledger has the plan snapshot immediately (open-flat can fire on continuation wander); a rejected seed (`plan.seed.rejected`) emits nothing (ledger and model see the same empty plan). Marathon state keeps an **internal carry chain** — up to the last 3 ancestor prompts in the carried-plan chain, each clipped to 500 chars, oldest first; reset on carried-plan drop / marathon off / chat change / `/new`; **never published to clients and never in the agent prompt**. `buildDigest` adds `carriedFrom` (ancestors only) + `plan.seededRevision` (the marathon carried-plan revision) when the turn was seeded, so the judge learns the originating task behind a "continue" prompt; the current prompt stays `task`. The agent prompt itself is unchanged (M2 carried plan + marathon guidance). Cadence: first call 4 min, then 6 min ±15% jitter, 10 min after two consecutive `progressing`, back to 4 otherwise; a `suspect` assessment brings a call forward (≥90 s floor); budget 40 calls / 150k input tokens per turn, then deterministic-only plus one notice (held while an alert is open, because every client shows the latest notice and it would hide the alert); 429/timeout skips and doubles the next interval once; two-strike rule — a `stuck`/`blocked` verdict (confidence ≥0.6) alerts only if a deterministic signal corroborates (`source:'both'`) or the previous verdict was also not `progressing` (`source:'watcher'`). It NEVER steers, stops, sends a bridge command, captures, changes `ok`/`label`/`plan`/`docsVerification`, or triggers a retry. One open notice; kind-change or 15-min re-alert; ≤3 alerts and ≤3 pushes per turn; **V2 recovery needs evidence** — a mid-turn alert clears only when ≥2 effectful act results arrived since the alert (ok, not no-effect, not control) AND the alert's own signals have been absent for 2 consecutive ticks, OR the plan's completed count rose since the alert; a plan revision alone or marking items blocked never clears it; "It's fine" snoozes a mid-turn alert kind 15 min. **V1 lifecycle:** every open notice is closed by an explicit `chat.watch` frame (`state:'closed'`, carrying its own id) — a mid-turn alert still open at turn end closes with reason "Turn ended.", and an `ended-incomplete` notice (emitted on an unfinished/blocked/dead/error marathon ending; help/confirm ends are exempt — the request itself is the user-facing notice) supersedes the mid-turn alert as the one open notice, is dismissable ("It's fine" → 200, no snooze), and closes at the next turn start ("A new turn started.") before the new turn's first frame, so the amber state never carries into a new turn. `/new`, a real chat switch, and marathon off clear everything. Alerts travel as `chat.watch`/`remote.watch`; the per-turn `watch {checks, alerts, usage}` summary is additive on `chat.done`/`chat.stopped`. Timers are injected for tests and `.unref()`'d in production.
- **A watcher verdict is a diagnostic, not verification.** "Progressing" does not mean the work is correct; "stuck" does not mean it failed. Acceptance still uses independent checkers. The judge is low-effort, text-only, cadence-sampled (plan decisions #3/#4) and — since V5 — pins provider routing + a fixed seed for verdict stability: it catches sustained obvious stalls and every hard signal, and the pre-V5 temp-0 instability that let intermittent varied-activity wander read as `progressing`/`unknown` is resolved by pinned routing (V5 gated stuck caught 1.000 / stability 1.000 on both tune and holdout, k=5). M4 acceptance used FALLBACK A — commit the best zero-false-alert configuration and record the gap: stuck-window detection 6/9 (67%) against the ≥80% target (distinct-run 6/7 = 86% is nuance, not the gate). **V5 closed the instability gap** (kept change: pinned morph/fp8 routing + fixed seed, effort still low): the temp-0 verdict flips were OpenRouter provider load-balancing, not effort — pinning routing made verdicts deterministic (stability 1.000 across k=5) and lifted gated stuck caught to **1.000 mean on BOTH tune and holdout** (clean bounce-form 0.6→1.0 stable), FA 0 worst, cost ≤V4. Candidate 1 (plan-progress history) gave only a noise-rise; candidate 2 (medium-requested effort + max_tokens 1200) was contaminated-driven and regressed the clean target — neither kept (at most one judge change, decision #6). V4 closed the continuation-plan-snapshot gap (an accepted M2 seed now emits one seeded plan activity at turn start). Open judge follow-ups are in `docs/STATUS.md`: long-turn length cutoffs at `max_tokens` 400 (V5.1) and a per-turn budget that the 90 s suspect trigger spends in about 35–45 minutes.
- **Hard stalls do not depend on the model.** Silence, a hung tool, and a lost executor alert deterministically, including when the judge is unavailable, over budget, or returns `unknown`. The judge can never veto a hard signal.
- **Watcher input is untrusted.** Digest content (tool results, page text, the plan) can never widen what the watcher does, because it can do nothing; the judge output is schema-validated (`validateVerdict` → `unknown` on any deviation) and the reason is rendered as plain text, never markdown or HTML.
- **Watcher cost is reported separately** from agent usage: the per-turn `watch.usage` counts judge tokens, and judge calls plus input/output/reasoning/cacheRead tokens are logged apart (`watch.judge.*`).
- **Automatic updates fail closed:** `companion/updater.mjs` moves only a clean checkout of the official repository that sits exactly on the running version's release tag, only to a newer published non-pre-release, only while no turn runs, marathon is off, and about ten idle minutes have passed, and only under a supervisor (`CRAZYAGENT_SUPERVISED=1`: `npm run dev`, the service). It never forces a checkout, resets, cleans, or touches `.dsh-home` state other than `update-state.json`; a failed install restores the previous tag. Exit code 75 means "restart me". The extension reloads itself only when its on-disk manifest is newer, seen twice 20 s apart, nothing is executing, and at most once per version (`extension/self-update.js`). A development checkout on a branch is never updated. The sidebar receives authoritative state through `chat.hello` and `update.state`; pending/installing/failure notices are informational and dismissible, never an approval requirement, and a completed update is announced once after restart.
- **Remote API** (`--remote`, `127.0.0.1:17873`, tailnet-only Serve, its own `0600` token) can never claim `ui`/`tools`, send browser commands, configure the LLM, or read arbitrary files. Port `17872` is the e2e fixture server.
- **One executor at a time:** the side panel or the background service worker, handed over explicitly. System-clipboard work needs the panel. A panel closed mid-turn leaves its debugger session attached; the next executor detaches a session of its own extension (Chrome lets only the attaching extension detach) and re-attaches once, and only a foreign debugger stays `DEBUGGER_BUSY` ("DevTools or another extension"). A panel that connects mid-turn shows the running turn (`chat.hello.turn`, status `thinking`) instead of sending `chat.new`. `browser_navigate` from a browser page (`edge://`, `chrome://`, extension pages; not `about:`) opens the destination in a new tab and leaves the browser page as it was: Edge kept refusing trusted input on a tab navigated in place away from its new-tab page. `browser_upload` finds the assigned input by its token, not its position; a page that swaps in a fresh input after the change event carried exactly the file (Gmail compose) reports `inputReplacedByPage` change-event evidence, which is not proof the page kept the file.
- **What people see:** no hitboxes on the page (they are drawn only into the model's copy of a capture; people get the clean `displayImage`), and one yellow agent cursor that fades out for every capture.
- **Android:** the reducer must match frames recorded from the real `RemoteHub` (`npm test` fails when stale). Toolchain under `~/Android`. Firebase is configured on this computer (`pushConfigured: true`, a `validate_only` send returned 200). The phone stays paired with `conan-evo-x3`, the designated push sender (2026-11-16 decision); logs copied from that machine show the app registered and FCM accepted 48 of 49 `done`/`help` sends (2026-11-16 to 11-18; the one `invalid-token` went to the phone's previous registration). FCM acceptance is not delivery: the phone showing a notification and the tap opening the turn are still unverified. Do not re-pair the phone to this computer.
- **Prompt budget:** model guidance stays under the test-enforced 17,100-character ceiling.

## Repository safety

- Do not fork DSH core or hand-edit generated `.dsh-home/browser-agent/llm.patch.yml`.
- Do not run live-model acceptance in unit tests; use fake bridges or isolated browser profiles. Keep test credentials and user data isolated.
- Never kill browsers by executable path. Stop only PIDs/PGIDs you started, scoped to the test profile.
- Reload the unpacked extension and reopen its panel after `extension/` changes. Restart the companion after companion, provider, or config changes.
- When changing documented behavior, update this file, `docs/STATUS.md`, or the relevant project doc in the same change.
