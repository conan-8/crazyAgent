Pre-input `STALE_VIEW`/`AMBIGUOUS_VIEW`/`NO_VIEW` refusals of `click_at`/`select`/`drag` return `attempted:false` with a fresh full view and stay refused until re-measured. DSH raises the model-switch failure before it commits the prompt, so that rerun resends the prompt itself; the others send a continue notice. - **Pointer-follow drags (2026-11-19 Browser Gauntlet log, current checkout):** on the gauntlet's Easy "Sort the mail" task every `browser_drag` that started on a letter failed with `DRAG_STALE_TARGET` "The source element moved or became covered before input completed" (7× over two turns; the task was then skipped, 7/8). A black-box replay of the executor's input on the real page in an isolated headless profile showed why: the letters are pointer-event widgets (no HTML5 drag) that translate the pressed letter under the cursor, so it moves ~460 px and covers the bin by the time of the drop. The pre-drop check demanded an unmoved, uncovered source, then released the mouse at (0,0), which snapped the letter back; a plain release on the bin files it. Revalidation now stays exact for both endpoints before hover and before the press. Before the drop the held source only has to stay attached, and the destination must be unmoved and the first element at the drop point apart from the dragged item: the pressed element (a coordinate press holds the deepest element, here the letter's `<b>` text), any ancestor that moved with it, or a same-text clone of either. An unrelated element over the destination, an unmoved source container raised over it, a moved destination, or a detached source still cancels. Stale-target messages now name the failed check, the stage (before input / before the press / before the drop), and the covering element. The same check also misreported the Medium "Rank by value" list: the old executor returned `DRAG_STALE_TARGET` while the row did move (the field log's "Order correct" after three failed drags); the fixed executor completes the drag and reports the change.
- **Evidence is separate from outcome:** results keep `observed`, `expectation`, `outcome`, and `mutationPossible` apart; a failed expectation never triggers re-aiming, retry, or re-mutation. DOM readback is not server persistence. Model-reported `DONE`/`PARTIAL`/`BLOCKED` labels, completed plan items, and `docsVerification` are not verification. URL-sensitive batch expectations (`export_contains`, `toolbar_style`) after a potentially document-changing step are rejected before side effects; page-scoped `text_landed` (a click) is allowed there and reports unknown on scope-mismatch — never a false verdict, no re-mutation (evidence validity only; each step's mutation guards still apply). Each turn records its leading label, `timings.failedCalls`, and per-turn token `usage`; `chat.done`/`chat.stopped` carry them and the panel/Android summaries show them.
- **Docs semantic fidelity:** exact `text-decoration` and ancestor underline/strike-through are preserved in export parsing. Checklist writes accept Google's flattened bullet+line-through export only with live checklist-control evidence and exported checked-state styling; they never infer checklist identity from bullets. Font additions can use exact `Remove <font>` evidence, require final toolbar verification, and close the Fonts modal on failure. Responsive formatting uses exact baseline export for uniform bold/italic/underline selections only after `CONTROL_NOT_FOUND`, with final export verification and no fallback on ambiguity.

- **Confirmation is opt-in and model-reported:** with `confirmIrreversible` off, behavior is unchanged. With it on, the model asks before irreversible actions and the chat waits for Approve/Deny, which the companion writes as the next turn's `<user_confirmation>` block (people see `Approved: …`/`Denied: …`, never the block). An executor backstop covers a turn that skips the tool: in a guarded turn that did not start from Approve, `click`/`click_role`/`batch`/`type` commands are stamped and the executor refuses, before input, a control matching the reviewed `CONFIRM_GUARD_PATTERN` verbs (or a native POST-form submit, or `submit:true`) with `CONFIRMATION_REQUIRED`. Enter-key submits and coordinate clicks are not covered. A confirmation wait is not verification that the action was safe.
- **DSH deep-freezes committed events:** help, confirmation requests, plan outcomes, and Docs verification travel as bridge activities (`help-request`, `confirm-request`, `turn-outcome`) accepted only for the active turn and session — never annotated onto `turn/end`.
- **One runner, one turn slot:** chat/new/stop/resume/steer/snapshots go through `companion/session-controller.mjs`, shared by the panel and the remote API; the marathon switch changes only through the same controller's `setMarathon`. One executor at a time (panel or background worker, explicit handover); system-clipboard work needs the panel. Viewport captures never take focus and keep working unfocused/minimized.
- **Remote API + Android:** opt-in `--remote` listener on `127.0.0.1:17873` (tailnet-only Serve, own `0600` token) can never claim `ui`/`tools`, send browser commands, configure the LLM, or read arbitrary files; port `17872` is the e2e fixture server. The Kotlin/Compose app (`android/`, API 26+) pairs with a Keystore-encrypted token, streams `/events` with replay/resync, sends/stops/new, Continue and Steer, live view + on-demand capture, help and approval cards, and push registration. Its reducer is pinned to frames recorded from the real `RemoteHub` (`scripts/remote-protocol-fixtures.mjs`; `npm test` fails when stale).
- **What people see:** no hitboxes on the page (burned only into the model's capture copy; people get the clean `displayImage`), and one yellow agent cursor that fades out for every capture. Sidebar activity uses friendly action summaries (`Clicked “Control name”`, `Switched to “Tab title”`) without argument JSON, raw results, label/tab IDs, execution telemetry, or session IDs; reasoning and error cards omit those internal references too, while the debug log retains full diagnostics. Settings ends with an About section showing the current version and the last successful update's localized date/time, with an extension-manifest version fallback and an explicit empty state for fresh installations. Enter or Send on a blank composer sends the first queued message (immediately when idle, as a steer while busy; an empty queue is a no-op), and a wait step wears a stopwatch icon (`icon-step-wait`) instead of the generic tool wrench.

- **Drag handles that grow on hover are refused before the press:** the pre-press revalidation still requires the source box to be unchanged since it was measured, and the gauntlet Medium "Wire the flowchart" ports (SVG `circle`) grow from 11.8 to 15.2 px around the same center when hovered. `browser_drag` therefore stops with `DRAG_STALE_TARGET` "moved before the press; nothing was pressed" (old and new executor alike); in the field run the agent drew the edges with `browser_select` instead. - **Docs checklist verification when toolbar controls are inaccessible — resolved 2026-11-19:** below about 1300 CSS px (a docked side panel leaves ~1160) Docs moves the list buttons into an overflow and marks its More button `aria-disabled="true"`, but clicking More still opens the overflow, where the real Checklist/Numbered/Bulleted buttons expose `aria-pressed` (live DOM check, isolated signed-in profile). - **Edge 157 download isolation:** Edge 157.0.4341.46 no longer honors `Browser.setDownloadBehavior` for `chrome.downloads` API downloads (the `browser_download` path) — they land in the profile default `~/Downloads` even with a persistent-session CDP override. - **Edge 157 cursor worker match:** Edge 157 ships built-in extensions whose service workers are also named `background.js`; the cursor suite matches the unpacked extension by id instead of by worker URL (commit `fa475d9`). Test-only.
- **Display idle / headless:** when the host display idles/locks it stops producing compositor frames, freezing WAAPI/rAF for **headed** Edge windows (enter/exit animations stall at frame 0; rAF probes hang). `--headless=new` is unaffected. UI previews use the `EDGE_BIN` override → a headless wrapper and finish started animations before captures; the `capture` suite is headed by design (its viewport/image assertion needs a painted, focused OS window) and fails on an idle/locked desktop. The Q5 gate table records each suite's headless/headed mode.
- **Google Docs behavior facts (learned during C2, 2026-11-16):** `Input.insertText` does **not** replace the document selection — it inserts at the caret, so selection-based writes must Delete the proven selection first; the find bar retains the previous query and its match counter lags a query change, so resolve occurrences only on a settled counter; Shift+ArrowRight on a find text-selection traverses **characters**, so collapse to cell end (ArrowRight) before extending across cells for merge; the custom-colour picker parses the hex box on **key events**, not inserted text, so send a caret key and read back the R/G/B fields before OK; the cell-background palette grid reflows as it opens, so wait for a stable palette before clicking a preset; positional structure commands ('Insert row below') act on the caret, so prove the cell selection first. Each is guarded by a positive-signal wait + fail-closed timeout + export verification.
- **Google Docs export and style facts (learned 2026-11-19 from field exports and a live disposable doc):** the HTML export gives a paragraph's **last** run a full explicit property set (color, weight, decoration, size, family, style) and earlier runs only what differs from the element/class rules, so splitting a run moves explicit values to inherited ones without any visible change; a heading span that keeps its style's weight carries no `font-weight` and inherits it from `h1{}`–`h6{}`; Title/Subtitle are `<p class="title|subtitle">` whose class rules sit over `p{}`; spaces next to a span boundary export as `&nbsp;`; applying a named style to the caret paragraph resets the caret's look, color included, to that style (a Subtitle typed gray with no color command); the Find and Replace fields stay in the DOM when closed (aria-hidden, unreachable), so "open" must mean visible and hit-reachable. A user's account can redefine the named styles (here Title 36 pt bold, Heading 1 24 pt bold, Subtitle 24 pt Georgia italic gray), so expected style looks must come from each document's export, never from Google's defaults.
