## Current behavior

- **Tools:** 34 standing model-facing tools (25 general browser, 8 guarded Docs, `agent_request_help`). `/marathon` (unlisted legacy alias `/plan`) conditionally arms `browser_plan` for every turn that starts while the companion-owned marathon switch is on; the companion's opt-in `confirmIrreversible` setting conditionally arms `agent_request_confirmation` for its turns. Both conditionals coexist; the standing count never changes. Mutations run exclusively in model order; only `browser_tabs`, `browser_places`, `browser_read_text`, `browser_docs_read`, and `browser_downloads` are parallel-safe (runtime max 4).
- **Marathon switch + carry-over + watcher + judge + phone (M1–M5 landed 2026-11-16; M6 release docs ship with v2.4.0 per `MARATHON-PLAN.md`):** one sticky, companion-owned switch (`companion/marathon.mjs` + `SessionController.setMarathon`), shared by the panel (`marathon.set` → `marathon.state`, also in `chat.hello`) and the remote API (`POST /marathon`, idempotent per `clientCommandId`). The sidebar chip renders only from `marathon.state` (no optimistic flip); its × turns the switch off. A legacy `planMode:true` message (old APK `/plan`) turns the switch on with the sender's origin, then arms the turn. The switch resets to off on `/new`, a real chat switch, and companion restart. A mid-turn toggle never re-arms the running turn: it keeps `browser_plan` to the end; the next turn picks the new state up. `chat.done` carries `marathon` beside `planMode` (both emitted this release); the hub journals `remote.marathon` and `/state` gains `marathon {enabled, since, plan, watch}`. **M2 carry-over:** a turn ending with open plan items carries the list into the next turn (`plan.mode {seed}` → `seedPlanState`, fail-closed `plan.seed.rejected` fallback to an empty plan); the `MALFORMED_RESPONSE` rerun re-seeds with the current snapshot; the panel renders the carried list at turn start. Nudges/stale reminders refill per accepted revision (2 per stretch) under a 12-per-turn lifetime cap; `staleAfterActivities` (6) and `maxItems` (40) unchanged. A seeded-but-untouched turn (no `browser_plan` call, zero tool results) answers `not-assessed` without nudges. The `<marathon_mode>` guidance block is per-turn text outside the 17,100 ceiling, fixed part 1,233 chars (≤1,500), carried list capped at 8 open-item lines; the carried header stresses continuation fidelity (completed items final, resume from the first open item, verify page state before re-acting — task-10 tuning). **M3 watcher:** a pure ledger (`watch-ledger.mjs`) records every turn; `assess()` applies the signal table; `watcher.mjs` ticks 20 s on a marathon turn and alerts on hard signals (SILENT_STALL 300 s / TOOL_HANG 240 s / EXECUTOR_DOWN 120 s) without the model; soft signals are diagnostic. The watcher only reports — it never steers/stops/mutates. One open alert, kind-change/15-min re-alert, ≤3 alerts+pushes per turn, recovery (3 ok incl. mutation or a plan revision), "It's fine" snooze, `ended-incomplete` on unfinished/blocked/dead/error endings. Alerts travel as `chat.watch`/`remote.watch`; the panel shows a watch row (Stop/Steer…/It's fine, collapses on recovery) and an amber chip; `/state marathon.watch.open` is the open-alert surface; `chat.done`/`chat.stopped` carry an additive `watch {checks, alerts, usage}` summary. **M4 judge:** `watch-judge.mjs` makes ONE stateless tool-less chat-completions call per check (injected key/baseUrl/model getters; key only in the Authorization header, never logged); cadence first 4 min then 6 min ±15% jitter, 10 min after 2×progressing, suspect brings a call forward (≥90 s floor); budget 40 calls / 150k input tokens per turn then deterministic-only + one notice; 429/timeout backoff; two-strike rule (a stuck/blocked verdict alerts only with deterministic corroboration or a prior non-progressing verdict); strict schema validation → `unknown` on any deviation; bounded per-turn ledger aggregates + `REVISIT_HINT` soft signal (never alerts alone). The judge is a diagnostic, not verification; hard signals alert without it and it can never veto them. **M5 phone:** `/marathon` slash (legacy `/plan` alias), marathon chip (visible+tappable while busy), watch card (Stop/Steer/It's fine), collapsible plan checklist, and a `WATCH` push type (dedupe `turnId:type:ordinal`). **Watcher deviation (FALLBACK A):** stuck-window detection 6/9 (67%) vs the ≥80% target — see Known limitations; zero false alerts on healthy runs is met.
- **Fail closed:** ambiguity, stale/drifted views, unsupported frames, paths outside Downloads, and unavailable colors fail with a code instead of guessing. ctrl/cmd+W is rejected in code. Pre-input `STALE_VIEW`/`AMBIGUOUS_VIEW`/`NO_VIEW` refusals of `click_at`/`select`/`drag` return `attempted:false` with a fresh full view and stay refused until re-measured. Drag/selection on iframe/canvas/video surfaces reports `unknown`, never a measured no-op. Two consecutive `SIDE_PANEL_CLOSED` results open a provider circuit that fails later browser calls at once until one succeeds, a new turn starts, or a bounded probe passes.
- **Dead model steps stay in the same turn:** a step whose tool call arrived as DSML text (or an empty step before any tool call) gets at most two `agent.steer` notices; an output-token (max-tokens) cutoff is continued the same way, keeping the turn's conditional tools armed. Internal notices use visible source kinds (`agent-notice`, `token-limit-continuation`). A reply the runtime rejects as `MALFORMED_RESPONSE` before any action is rerun once by the companion with the turn's modes re-armed. A turn that still did nothing ends as `chat.error` ("The model's reply could not be used (MALFORMED_RESPONSE)…") or a `BLOCKED:` answer — never a blank success or raw markup. The panel also guards the **live stream**: leaked DSML text deltas are suppressed (mirroring the companion's `isLeakedToolCallText`), stripped from saved history, and never rendered as a reply row (`extension/sidepanel/leaked-markup.js`).
- **Evidence is separate from outcome:** results keep `observed`, `expectation`, `outcome`, and `mutationPossible` apart; a failed expectation never triggers re-aiming, retry, or re-mutation. DOM readback is not server persistence. Model-reported `DONE`/`PARTIAL`/`BLOCKED` labels, completed plan items, and `docsVerification` are not verification. URL-sensitive batch expectations (`export_contains`, `toolbar_style`) after a potentially document-changing step are rejected before side effects; page-scoped `text_landed` (a click) is allowed there and reports unknown on scope-mismatch — never a false verdict, no re-mutation (evidence validity only; each step's mutation guards still apply). Each turn records its leading label, `timings.failedCalls`, and per-turn token `usage`; `chat.done`/`chat.stopped` carry them and the panel/Android summaries show them.
- **Confirmation is opt-in and model-reported:** with `confirmIrreversible` off, behavior is unchanged. With it on, the model asks before irreversible actions and the chat waits for Approve/Deny, which the companion writes as the next turn's `<user_confirmation>` block (people see `Approved: …`/`Denied: …`, never the block). An executor backstop covers a turn that skips the tool: in a guarded turn that did not start from Approve, `click`/`click_role`/`batch`/`type` commands are stamped and the executor refuses, before input, a control matching the reviewed `CONFIRM_GUARD_PATTERN` verbs (or a native POST-form submit, or `submit:true`) with `CONFIRMATION_REQUIRED`. Enter-key submits and coordinate clicks are not covered. A confirmation wait is not verification that the action was safe.
- **DSH deep-freezes committed events:** help, confirmation requests, plan outcomes, and Docs verification travel as bridge activities (`help-request`, `confirm-request`, `turn-outcome`) accepted only for the active turn and session — never annotated onto `turn/end`.
- **One runner, one turn slot:** chat/new/stop/resume/steer/snapshots go through `companion/session-controller.mjs`, shared by the panel and the remote API; the marathon switch changes only through the same controller's `setMarathon`. One executor at a time (panel or background worker, explicit handover); system-clipboard work needs the panel. Viewport captures never take focus and keep working unfocused/minimized.
- **Remote API + Android:** opt-in `--remote` listener on `127.0.0.1:17873` (tailnet-only Serve, own `0600` token) can never claim `ui`/`tools`, send browser commands, configure the LLM, or read arbitrary files; port `17872` is the e2e fixture server. The Kotlin/Compose app (`android/`, API 26+) pairs with a Keystore-encrypted token, streams `/events` with replay/resync, sends/stops/new, Continue and Steer, live view + on-demand capture, help and approval cards, and push registration. Its reducer is pinned to frames recorded from the real `RemoteHub` (`scripts/remote-protocol-fixtures.mjs`; `npm test` fails when stale).
- **What people see:** no hitboxes on the page (burned only into the model's capture copy; people get the clean `displayImage`), and one yellow agent cursor that fades out for every capture. Enter or Send on a blank composer sends the first queued message (immediately when idle, as a steer while busy; an empty queue is a no-op), and a wait step wears a stopwatch icon (`icon-step-wait`) instead of the generic tool wrench.
- **Default model:** OpenRouter `deepseek/deepseek-v4.1-flash-1017` — the pinned 1017 snapshot — at medium reasoning. Every live default references it: the panel's recommended-model constant, the companion's `RECOMMENDED_MODEL_ID`, the saved `llm.json`, `config/browser.patch.yml`'s compaction `modelPolicies`, `config/crazyagent.service` (and the installed unit), the eval-harness defaults, and the README install instructions. The un-pinned `deepseek/deepseek-v4.1-flash` alias survives only in dated run records (baselines and history sections), which keep the ID actually requested at run time.

## Known limitations

- **Live-stream markup guard residual:** a DSML tag split mid-tag across deltas can flash a brief incomplete fragment before the next delta completes the tag and the guard removes the row; the guard catches it as soon as the tag completes. Companion-side buffering of streamed text is deliberately **not** built. The committed answer/error and saved history are always clean.
- **Watcher v1 deviation (M4 FALLBACK A, lead ruling):** the low-effort, text-only, cadence-sampled judge (plan decisions #3/#4) catches sustained obvious stalls and every hard signal, but **intermittent varied-activity wander** can read as `progressing`/`unknown`. The gate is stuck **WINDOWS** flagged within two checks = **6/9 (67%)** against the ≥80% target (distinct-run 6/7 = 86% is nuance, not the gate); FALLBACK A commits the best zero-false-alert configuration and records the gap. **Zero false alerts on HEALTHY/PROGRESSING runs is met** (0/53 replay fine windows; M4 live 15/15 zero healthy false alerts). **Label correction (lead):** `m0Stall-r4` is a STUCK true positive (140 s inert loop + PLAN_STALLED + judge stuck@140 s precedes its honest BLOCKED@153 s by 13 s; plan §0/§5 M4/§2.3 consistent) — lead's earlier "zero alerts on honest runs" framing was over-strict (acknowledged); an alert preceding an honest BLOCKED end on a genuinely looping run is desired. **Non-determinism:** the temp-0 judge still varies run-to-run; the earlier "0 fine false alerts" was partly luck — the **3/53 ≈ 0.057** false-alert rate caveat applies (small sample, correlated late slices). A watcher verdict is a diagnostic, not verification; completing-wander-with-redos is a correctness failure caught by independent server-side checkers, not a watcher "stuck" failure.
- The confirmation gate is model-reported first; the backstop does not cover Enter-key submits or coordinate clicks, and a confirmation wait is not safety verification.
- Remote browser execution needs an awake host, a running companion, and running Edge (the side panel need not be open). System-clipboard work needs a panel.
- Never expose the privileged bridge (`17871`) or remote controller (`17873`) through Tailscale Funnel or an unauthenticated public listener.
- **Android JVM timing flakes hardened (test-only):** `RemoteControllerTest` asserted asynchronous pending-store and retry effects too early. The save/clear assertions now use bounded `awaitStoreSaved`/`awaitStoreCleared` polls with a generous 15 s `await`. The CI recurrence (run 43871229019, `aLostConfirmAnswerIsRetriedOnlyWithTheSameId` `assertEquals(3, messagePosts.size)`) was the lost-answer **retry-post race**: the reconcile loop's same-ID retry post lands after `UiState.pending` clears, so the count assertion saw 2 instead of 3. Fixed with `awaitAnswerRetriedOnce()` — a bounded poll for the retry post recorded AND the answer run exactly once before the count/ID assertions; if the retry never lands it times out and fails correctly (it does not mask a delivery regression). `tearDown` now joins the run loop (closing its WebSocket) before `server.close()` and releases the OkHttp threads, which cleared the full-class systemic stall (resource accumulation across sequential tests). Production code unchanged. Proof: 20/20 then 30/30 isolated, 10/10 under moderate scoped load, 8/8 full-class reruns, full `testDebugUnitTest` 97/0 failures/1 opt-in skip, lint clean. **Residual:** a very rare upstream `UiState`-await timeout (~1 in 50 isolated runs, upstream of the retry assertion — event-stream scheduling) was still observed once; test-infra suspected, **not a proven production race**. Revisit only if it recurs in CI.

## Environment notes

- **Edge 157 download isolation:** Edge 157.0.4341.46 no longer honors `Browser.setDownloadBehavior` for `chrome.downloads` API downloads (the `browser_download` path) — they land in the profile default `~/Downloads` even with a persistent-session CDP override. The harness/gate runner now writes the throwaway profile's `Default/Preferences` `download.default_directory` **before** Edge starts and keeps the CDP override for navigational downloads (commit `f9324ad`). The 2026-11-11 download-upload baseline predates the Edge update.
- **Edge 157 cursor worker match:** Edge 157 ships built-in extensions whose service workers are also named `background.js`; the cursor suite matches the unpacked extension by id instead of by worker URL (commit `fa475d9`). Test-only.
- **Display idle / headless:** when the host display idles/locks it stops producing compositor frames, freezing WAAPI/rAF for **headed** Edge windows (enter/exit animations stall at frame 0; rAF probes hang). `--headless=new` is unaffected. UI previews use the `EDGE_BIN` override → a headless wrapper and finish started animations before captures; the `capture` suite is headed by design (its viewport/image assertion needs a painted, focused OS window) and fails on an idle/locked desktop. The Q5 gate table records each suite's headless/headed mode.
- **Google Docs behavior facts (learned during C2, 2026-11-16):** `Input.insertText` does **not** replace the document selection — it inserts at the caret, so selection-based writes must Delete the proven selection first; the find bar retains the previous query and its match counter lags a query change, so resolve occurrences only on a settled counter; Shift+ArrowRight on a find text-selection traverses **characters**, so collapse to cell end (ArrowRight) before extending across cells for merge; the custom-colour picker parses the hex box on **key events**, not inserted text, so send a caret key and read back the R/G/B fields before OK; the cell-background palette grid reflows as it opens, so wait for a stable palette before clicking a preset; positional structure commands ('Insert row below') act on the caret, so prove the cell selection first. Each is guarded by a positive-signal wait + fail-closed timeout + export verification.
- **Docs test profile developer mode:** Edge resets `extensions.ui.developer_mode` to off on restart, which disables the unpacked extension (`disable_reasons` 16777216 = DISABLE_UNSUPPORTED_DEVELOPER_EXTENSION). The isolated `~/.cache/crazyagent/docs-profile` prefs now persist `extensions.ui.developer_mode=true` (backup at `/tmp/docs-prefs-backup.json`) so the extension loads after restart. Test-profile only.
- **In-process session resume (task-16):** phone Continue on a saved chat from the **same** companion process now works — direct resume for an unowned target; an owned target ('already open or opening') is restored via teardown → fresh runtime → resume from disk (the SDK has no per-session close RPC); a failed restore keeps the current chat and returns `SESSION_NOT_RESUMABLE`. The post-restart path is preserved. Verified both paths through the real runtime (C1 resume row).
